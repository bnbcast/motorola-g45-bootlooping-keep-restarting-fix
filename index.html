The Problem

Your Moto G45 5G reboots every ~2 minutes. Factory resets and firmware flashes don't help. Understanding why is the first step to fixing it.

Symptom: The 2-Minute Bootloop

The phone boots normally, operates for approximately 2 minutes, then reboots. This cycle repeats indefinitely. The loop persists through OTA updates, LMSA firmware flashes, and factory resets.

Why Standard Fixes Fail

  • OTA / LMSA flashes rewrite AP partitions only — never touch modemst1/2
  • Factory reset masks the issue for ~3 hours by re-provisioning the modem stack
  • Disabling apps reduces crash frequency but doesn't address the modem
  • Custom ROMs replace Android, not the modem firmware or its NV storage

The Crash Fingerprint

Every reboot generates a qcrilNrd crash with SIGSEGV at address 0xffffffffffffff02 (-254 used as a pointer). This is the definitive signature of corrupt modem NV.

Root Cause Analysis

Two processors, one broken communication channel. Here's what happens under the hood.

The device contains two independent computers: the Application Processor (AP) running Android, and the Modem/Baseband handling radio, SIM, calls, and mobile data. They communicate over Qualcomm's OEM Hook channel, brokered by the RIL daemon qcrilNrd.

The Failure Chain

  1. Corrupt NV Database: The modem's non-volatile memory (modemst1/modemst2) is corrupted. On every boot, the modem fails its consistency check and asserts.
  2. QMI Services Vanish: The modem's QMI (Qualcomm MSM Interface) services never come up. The communication channel goes silent.
  3. Dead Token Dereference: Motorola's proprietary library libmotext_inf.so attempts to send an OEM hook message using a token for a connection that no longer exists (-254 used as a pointer).
  4. SIGSEGV in qcrilNrd: The invalid memory access crashes the RIL daemon.
  5. System Server Blocks: system_server waits on a Binder call that will never return.
  6. Watchdog Reboot: After ~60 seconds, the hardware watchdog forces a reboot. The cycle repeats every 2 minutes.
Key insight: The qcrilNrd crash is a symptom, not the cause. The root cause is the corrupt modem NV database. Erasing modemst1/2 allows the modem to rebuild NV from the pristine fsg partition.

Prerequisites

This is not a phone-only repair. You need a PC, a data cable, and preparation. Most failures happen before the first command.

Critical Requirements — Read Before Starting
  • Unlockable bootloader — Motorola only unlocks retail units (XT2363-9 is retail). fastboot erase is refused while locked.
  • Record IMEI first — Dial *#06# and write both numbers down. The erase wipes the NV store holding IMEI.
  • Full backup before unlock — Unlocking wipes /data (WhatsApp keys, 2FA seeds, everything). See backup guide.
  • Do NOT relock — Relocking a modified boot chain (erased modemst1/2) will hard-brick the device.

Hardware & Environment

  • Windows 10/11 PC with admin rights (Motorola LMSA is Windows-only)
  • USB data cable — not charge-only (common failure point)
  • Direct USB port — no hubs or docks
  • 30–60 GB free disk space

Software Setup

  • Android SDK Platform-Tools (ADB + Fastboot)
  • Motorola LMSA / Rescue and Smart Assistant
  • Internet on PC for unlock code & firmware

Phone Configuration

  • USB Debugging enabled + "Always allow from this computer"
  • Screen lock set to None temporarily
  • Battery > 50%
  • Google account password known (FRP)
  • 2FA seeds exported, backups complete

5

Erase the Modem NV Partitions

Boot into fastboot mode (Power + Volume Down), then run:

# Erase both modem NV partitions
fastboot erase modemst1
OKAY [  0.139s]

fastboot erase modemst2
OKAY [  0.005s]

# Reboot — modem rebuilds NV from golden fsg partition
fastboot reboot

The modem automatically reconstructs a clean NV database from the pristine fsg partition on first boot. This is the actual fix.

Frequently Asked Questions

Quick answers — full details in the GitHub FAQ.

Will this fix survive OTA updates?
Yes. OTA updates rewrite AP partitions (boot, dtbo, vendor_boot, super), not modemst1/2. The rebuilt NV persists unchanged.
Can I do this without unlocking the bootloader?
No. fastboot erase modemst1/modemst2 is explicitly refused while the bootloader is locked. Motorola's official unlock is required (retail units only).
Is my IMEI at risk?
The erase wipes the NV store holding IMEI, but the modem rewrites it from the golden fsg partition on first boot. Record it first (*#06#) and verify after. Ours matched exactly.
Does a custom ROM (LineageOS, Pixel Experience, etc.) fix this?
No. Custom ROMs only replace AP partitions. They never touch modemst1/2. The modem firmware and its NV storage are completely separate from the Android OS.
Factory reset appeared to work for 3 hours — why?
Factory reset re-provisions the modem stack (rewrites /data/vendor/radio, clears telephony DB), which temporarily masks corrupt NV. But it never touches modemst1/2, so the corruption persists and the loop returns.
What is the qcrilNrd crash really?
A symptom, not the cause. The modem's QMI services vanish due to corrupt NV. Motorola's libmotext_inf.so then dereferences a token for a dead connection (-254 used as pointer) → SIGSEGV in qcrilNrd → system_server blocks → watchdog reboot.
Can I relock the bootloader after the fix?
No. Relocking with a modified boot chain (erased modemst1/2 = modified vendor state) will hard-brick the device. Leave it unlocked permanently.
Is this fix specific to build V1UGS35H.75-14-9-3-1-4?
The root cause (corrupt modemst1/2) and fix (erase both) are build-agnostic for any fogos device. The exact baseband version may differ; verify gsm.version.baseband is present after reboot.
